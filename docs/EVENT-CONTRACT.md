# Event Contract

This document is the single source of truth shared by the frontend and backend.
There is no HTTP API in this system, so this contract *is* the interface.

## 1. Transport

MQTT 5 over WebSockets. The browser is an MQTT client, the Python service is an
MQTT client, and neither ever addresses the other directly — they only publish to
and subscribe from topics on a broker.

```
┌────────────────┐                  ┌──────────┐                  ┌─────────────────┐
│  Svelte client │ ──── wss ──────► │  Broker  │ ◄──── wss ─────  │ Python asyncio  │
│   (browser)    │ ◄────────────── │(mosquitto│ ──────────────►  │    "kitchen"    │
└────────────────┘                  │ /HiveMQ) │                  └─────────────────┘
        ▲                           └──────────┘
        │  N browser windows all subscribe to the same state topics,
        └─ so every window renders identical state without talking to each other.
```

Browsers cannot open raw TCP sockets, so MQTT is tunnelled inside a WebSocket
frame. It is the same MQTT protocol; the WebSocket is only the carrier. The
broker must have a listener explicitly configured for the websockets protocol.

## 2. Topics

| Topic                              | Direction | QoS | Retained | Purpose                                   |
| ---------------------------------- | --------- | --- | -------- | ----------------------------------------- |
| `restaurant/table/{tableId}/order` | FE → BE   | 1   | no       | Customer places an order                  |
| `restaurant/kitchen/reset`         | FE → BE   | 1   | no       | Clear all state (demo affordance)         |
| `restaurant/table/{tableId}/state` | BE → FE   | 1   | **yes**  | Authoritative state of one table          |
| `restaurant/kitchen/status`        | BE → FE   | 1   | **yes**  | Kitchen online/offline (also the LWT)     |
| `restaurant/client/{clientId}/err` | BE → FE   | 1   | no       | Private rejection notice to one sender    |

The backend subscribes with a single-level wildcard, `restaurant/table/+/order`,
so adding tables needs no subscription changes.

### Why `state` is retained

A retained message is stored by the broker as the last known value of a topic and
delivered immediately to any client that subscribes *later*. This is the entire
answer to "open a second browser window and it must already know about existing
orders": the new window subscribes to `restaurant/table/+/state` and instantly
receives one retained message per table describing exactly what is cooking. No
REST snapshot endpoint, no replay protocol, no shared frontend state.

### Why errors are *not* retained and are per-client

A rejection is transient feedback for one sender. Retaining it would greet every
future window with a stale error. Addressing it to `{clientId}` means one
customer's validation failure is not broadcast to everyone, and it lets the broker
ACL restrict each web client to subscribing to its own inbox only.

## 3. Payloads

All payloads are UTF-8 JSON. The backend validates every inbound message with
pydantic and **discards** anything invalid (logged at WARNING) — a malformed
message must never break the consumer loop.

### 3.1 OrderPlaced — `restaurant/table/{tableId}/order`

```jsonc
{
  "clientOrderId": "b2c8...",   // uuid4, generated by the browser
  "clientId": "9f31...",        // uuid4, stable per browser tab; error return address
  "tableId": 3,                 // must match the topic and be a known table
  "foodName": "Pad Thai",       // 1..80 chars after trimming, no control characters
  "sentAt": "2026-07-29T18:04:11.123Z"
}
```

`clientOrderId` is an **idempotency key**. QoS 1 means *at least once* delivery,
so the broker may legitimately deliver the same publish twice (e.g. if the
client's PUBACK was lost and it retransmitted). Without a dedupe key the customer
gets two dishes for one click. The backend remembers recently seen
`clientOrderId`s and ignores repeats.

`tableId` appears in both the topic and the payload; the backend rejects a
mismatch rather than trusting either blindly.

### 3.2 TableState — `restaurant/table/{tableId}/state` (retained)

```jsonc
{
  "tableId": 3,
  "epoch": "5f2c...",           // identifies the kitchen generation
  "version": 7,                 // monotonic per table *within one epoch*
  "updatedAt": "2026-07-29T18:04:11.900Z",
  "orders": [
    {
      "orderId": "a41f...",     // assigned by the backend, canonical
      "foodName": "Pad Thai",
      "status": "COOKING",      // COOKING | SERVED | FAILED
      "placedAt": "2026-07-29T18:04:11.200Z",
      "cookSeconds": 23.4,      // the random cook time the kitchen assigned
      "expectedReadyAt": "2026-07-29T18:04:34.600Z",
      "readyAt": null           // set when status becomes SERVED
    }
  ]
}
```

### `cookSeconds` and `expectedReadyAt` are display data

The kitchen draws a random cook time **when it accepts the order**, not when the
cooking task starts, so the value is already in the first state message a client
receives and a countdown can start correct rather than a moment late. The cooking
task then sleeps for exactly that value, so there is one number rather than two
that could disagree.

To be unambiguous about where authority lives: **the backend's `asyncio.sleep` is
the timer.** An order becomes SERVED only when the kitchen publishes that
transition. These two fields exist so the UI can render a countdown and show the
assigned duration; a client that ignored, altered, or forged them could not make a
dish arrive sooner or later.

`version` lets the client drop a stale state message. On reconnect a client can
receive the retained message and a live update in an order it cannot guarantee,
so the rule is: **ignore any state whose `version` is not greater than the
version already held for that table.** This makes the frontend reducer safe
against duplicate and out-of-order delivery.

`epoch` bounds that comparison. Kitchen state is in-memory, so restarting the
kitchen resets every `version` to zero. A client holding version 5 would then
reject the restarted kitchen's version 0 as stale and keep showing orders that no
longer exist — permanently, since the versions never catch up. The full rule is
therefore: **compare versions only when the epoch matches; a different epoch is
always accepted.** This was found by restarting the backend with a browser open,
not by reading the code.

The whole table is sent on every change rather than a delta. Deltas would need
gap detection and resync; full-state-per-table is idempotent, trivially correct,
and the payload is bounded because orders per table are capped.

### 3.3 OrderRejected — `restaurant/client/{clientId}/err`

```jsonc
{
  "clientOrderId": "b2c8...",
  "tableId": 3,
  "reason": "TABLE_AT_CAPACITY", // machine-readable enum
  "message": "Table 3 already has 5 orders in progress."
}
```

Reasons: `VALIDATION_FAILED`, `UNKNOWN_TABLE`, `TABLE_AT_CAPACITY`,
`KITCHEN_AT_CAPACITY`.

### 3.4 Reset — `restaurant/kitchen/reset`

```jsonc
{ "requestedBy": "9f31..." }   // clientId, for the audit line only
```

Cancels every in-flight cooking task, clears all tables and the dedupe cache,
issues a **new epoch**, and republishes the cleared state so the broker's retained
slots and every connected client agree immediately.

Resetting is precisely the situation `epoch` exists for: versions restart at zero
and clients accept the state because the generation changed. The payload is not
trusted for anything — `requestedBy` is logged, never authorised against.

This is a demo affordance so a walkthrough can be restarted without restarting
processes. It is destructive and unauthenticated, so it is gated by
`RESTAURANT_ENABLE_RESET` and the broker ACL should not grant it to a public web
client in a real deployment. See [SECURITY.md](SECURITY.md).

### 3.5 KitchenStatus — `restaurant/kitchen/status` (retained)

```jsonc
{ "status": "ONLINE", "since": "2026-07-29T18:00:00.000Z" }
```

Published as `ONLINE` on startup and `OFFLINE` on graceful shutdown. The same
topic is registered as the client's **Last Will and Testament**, so if the backend
is killed or its network drops, the *broker* publishes `OFFLINE` on its behalf.
The UI can therefore distinguish "nothing is cooking" from "the kitchen is gone",
which no amount of frontend polling could tell you.

## 4. State machine

```
                 ┌──────────────────────────────┐
   ORDER ───────►│ COOKING  (random 10-30s)     │
                 └──────────────┬───────────────┘
                                │ timer elapsed
                                ▼
                        ┌───────────────┐
                        │    SERVED     │  (food visible on the table)
                        └───────────────┘
```

A table may hold several orders at once, each with an independent timer. This is
closer to a real restaurant than a one-dish-at-a-time lock, and it makes the
concurrency requirement observable: place orders on four tables within a second
and they complete in an interleaved order determined by their own timers.

`FAILED` exists for the case where a cooking task raises unexpectedly; the order
is marked failed and reported rather than silently vanishing.

## 5. Limits and validation

| Rule                         | Value | Rationale                                  |
| ---------------------------- | ----- | ------------------------------------------ |
| `foodName` length            | 1..80 | Bounds payload size; rejects empty input   |
| `foodName` content           | no control chars | Avoids log injection / broken UI |
| Orders in progress per table | 5     | Prevents one table flooding the kitchen    |
| Orders in progress globally  | 100   | Bounds process memory and task count       |
| Dedupe cache size            | 1000  | Bounded LRU; prevents unbounded growth     |
| Cook time                    | 10-30s (configurable) | Assignment requirement     |

## 6. Trust model

The browser bundle is public, so **any credential shipped to the frontend is
public**. This is stated plainly rather than pretended away. The mitigation is
least privilege at the broker, not secrecy:

- The web client connects as a dedicated broker user whose ACL permits
  **publish** only to `restaurant/table/+/order` and **subscribe** only to
  `restaurant/table/+/state`, `restaurant/kitchen/status`, and its own
  `restaurant/client/{clientId}/err`.
- Critically it may **not** publish to `.../state`. Otherwise a customer could
  forge "your food is ready" for any table, and the backend would not even be
  involved.
- The backend connects as a separate user permitted to publish state.

The genuine production fix — per-session credentials or JWTs minted by an auth
service and verified by the broker — is out of scope here and is recorded in the
README as a known limitation.
